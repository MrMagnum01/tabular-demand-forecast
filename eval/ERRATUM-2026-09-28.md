# Erratum, 2026-09-28 — round-2 HOLD clause 3, and the manifest-v2 successor binding

Astra's round-2 review (`~/vault/40-sessions/2026-09-28-astra-tabular-r2-review.md`) held commit `fdad847`
on two remaining MUST-FIX points after accepting runtime fixes 1/2/4 (no-plan forecast masking, strict
evaluator/protocol hash binding on forecast, no forecast overwrite). This erratum documents both fixes and
why a second manifest exists rather than editing the first one.

## Clause 3 — non-finite raw predictions could escape as "unavailable" or a clipped 0

Before this fix, `predict_gbm` (`src/tabular_demand_forecast/model_selection.py`) computed
`clipped = max(0, raw)` unconditionally, and `method_predictions`/`future_forecast`
(`src/tabular_demand_forecast/evaluate.py`) mapped a row to NaN ("unavailable") whenever the row's own
*plan* inputs were missing. Two failure modes followed:

* A model returning **NaN** raw output on a row whose plan inputs WERE available produced `max(0, NaN) = NaN`
  in the final predictions array — indistinguishable from a legitimately unavailable row. `stratum_report`'s
  own finiteness guard (`metrics.py`) never saw a problem, because from its point of view the row was simply
  "unavailable", and coverage/metrics looked normal instead of reporting a failed method.
* A model returning **-Inf** raw output on an available row produced `max(0, -Inf) = 0.0` — a finite,
  plausible-looking number — silently, before any finiteness check ran at all.

Fix: `predict_gbm` now checks the RAW prediction for finiteness against `gbm_available_mask` (the actual
input-availability signal — finite price and promo_flag) BEFORE computing the clipped value. A non-finite raw
value on an available row raises `MethodFailure` immediately; clipping is never reached for it, and it can
never be reported as "unavailable". A row whose plan inputs are genuinely missing is untouched by this check
and still yields NaN/"unavailable" as before. See `tests/test_model_selection.py::test_predict_gbm_raises_on_nonfinite_raw_for_available_row`,
`tests/test_model_selection.py::test_predict_gbm_genuinely_unavailable_row_is_not_a_failure`,
`tests/test_evaluate.py::test_method_predictions_raises_on_nonfinite_raw_for_available_input`, and
`tests/test_evaluate.py::test_future_forecast_raises_on_nonfinite_raw_for_available_plan` — the two probes
from Astra's review (`nan_model`, `neg_inf_after_clip` in
`~/vault/40-sessions/2026-09-28-astra-tabular-r2-review-probes.py`) are wired in as these tests.

This fix touches `model_selection.py`, which the round-1 fixes did not change. The successor manifest below
now binds five changed evaluator files in total: `model_selection.py` (this fix) plus `metrics.py`,
`provenance.py`, `evaluate.py` and `cli.py` (the round-1 fixes already accepted).

## Clause 2 integration / historical erratum — the quickstart could not pass on this head

`verify_run_environment` correctly refuses to run against `eval/manifest.json` once evaluator source differs
from what it recorded — and after the round-1 and round-2 fixes, five evaluator files differ from that
manifest (see above). That refusal is the gate working as designed, not a bug: `eval/manifest.json` is the
historical record for `results/`, produced and reviewed under the ORIGINAL evaluator source at commit
`12bdc69`, and it must keep describing exactly that code, unedited, forever. Astra's finding was that the
README's quickstart claimed this same manifest gates a `train`/`evaluate`/`forecast` run on the current
(fixed) head — which cannot be true once the gate is doing its job.

Fix: this repository now carries two manifests, not a versioned edit of one:

* **`eval/manifest.json`** — unchanged, byte-for-byte, from commit `12bdc69`. It binds the original evaluator
  source and is the provenance record for `results/`. It is never edited, and a run against it will keep
  refusing on today's source, as it should.
* **`eval/manifest.v2.json`** — new, generated by `scripts/write_manifest_v2.py`, binding the CURRENT
  evaluator source (the same protocol, the same pre-fit-freeze generator/features/calendar/protocol.py
  hashes, the same dependency lock — nothing about the frozen dataset or its protocol changed) with the five
  corrected evaluator file hashes. `verify_run_environment` now accepts an explicit `manifest_path` (CLI:
  `--manifest`), so `train`/`evaluate`/`forecast --manifest eval/manifest.v2.json` runs and gates cleanly on
  this head. `results/` is not touched by this: nothing was re-fit, re-selected or re-scored to produce
  `manifest.v2.json`, and no existing result is relabelled as having been produced under it.

The README's quickstart now uses `--manifest eval/manifest.v2.json` explicitly, and a separate "legacy
reproduction" note points at commit `e3e7b76` (the last commit before this HOLD-fix work; identical
evaluator source to `12bdc69`/`eval/manifest.json`) for anyone who wants to reproduce the ORIGINAL,
now-documented-as-defective run instead.

## The week-105 forecast artifact in `results/` is superseded, nonconforming output

`results/future_forecast_week105.csv` was produced under the pre-fix `future_forecast`, before clause-1 and
clause-3 were fixed. Its rows carry a numeric prediction with
`status=forecast_no_outcome_yet+plan_unavailable_native_nan_routing` for a week with no price/promo plan —
exactly the native-NaN-routed forecast clause 1 and the current `plan_missing_policy` say must never be
produced (a row with no plan should be `unavailable_plan`, no numeric prediction). It is kept, byte-unchanged,
as evidence of the pre-fix behavior; it is not deleted, not re-labelled as conforming, and not used as a
current forecast. The README's "Forecast for a future week" section marks it superseded/nonconforming and
points readers at a fresh `forecast --manifest eval/manifest.v2.json` run for a conforming week-105 forecast.

## What did NOT change

* `eval/manifest.json`, `eval/protocol.v2.json`, `eval/dependency-lock.txt`, and everything under `results/`
  are byte-identical to `fdad847`'s predecessor state. No fit, selection or score ran against the frozen
  dataset as part of this fix.
* No model provenance, selection log entry, or metric in `results/` was retuned, re-scored or relabelled.
* The frozen protocol (`eval/protocol.v2.json`, sha256 `a9604f02...e06b9eb`) is unchanged.
